# StableAMD v0.3 status

Last updated: 2026-09-22

StableAMD v0.3 is the active development line on `feat/stableamd-v0.3` / draft PR #4. The physical acceptance target remains Windows + AMD Radeon RX 6950 XT 16 GiB (`gfx1030`) with the managed TheRock/ROCm + PyTorch + ComfyUI runtime.

Automated GREEN is not physical acceptance. Features that have not completed their RX 6950 XT checklist are called out explicitly below.

## Target-accepted baseline

Accepted and maintained on the RX 6950 XT:

- native Windows AMD execution through the managed TheRock runtime;
- private CPython 3.12.10 and pinned ROCm PyTorch stack;
- managed loopback ComfyUI + StableAMD application process;
- SDXL txt2img/img2img/inpaint/outpaint and ordered MultiLoRA;
- Z-Image Turbo txt2img, model-only LoRA, native inpaint/outpaint, Canny, OpenPose and Depth;
- Krea 2 Turbo FP8 txt2img, model-only LoRA, OpenPose, Depth and whole-image Image Edit;
- automatic multi-person DWPose extraction;
- curated RealESRGAN / 4x-UltraSharp upscaling;
- Gallery/history, reuse/delete and async generation jobs;
- **Text-to-SVG v1** in the dedicated Vector workspace, covering text-free Icon / Logo mark and Vector Illustration workflows with managed VTracer, Clean SVG sanitization, transparent-background handling, PNG preview and SVG Gallery lifecycle.

The default 16 GiB stability policy remains:

```text
DynamicVRAM + RAM-pressure cache + CPU VAE
```

Provider-local overrides are used only where target-tested.

## Character Sheet v1 — visual acceptance failed

The first Character Sheet implementation generated independent views and later tried to recover identity consistency. Physical testing exposed identity drift, background/statue leakage and repeated artifacts. It remains only as the explicit `legacy-sequential` comparison path and is not target-accepted.

## Character Sheet v2 — implemented, automated GREEN, physical acceptance pending

Character Sheet v2 defaults to Krea 2 Identity Edit v1.2 with the pinned dependency:

```text
node pack: lbouaraba/comfyui-krea2edit
commit:    86f886dac23013d88996e3a2e99093ba44d322fb
LoRA:      krea2_identity_edit_v1_2.safetensors
SHA-256:   6adf9a69cc9502d286db7b69964d37da7e9cfe4b05b4d004bc275f087d3fd3cf
```

The base sheet is one `1792 x 1024` generation:

```text
FACE | FRONT | 3/4 | SIDE | BACK
```

The accepted architecture keeps the first identity detail reference face-only. FACE/FRONT/3/4 can then run the guarded tighter identity correction pass; SIDE remains profile-safe and BACK never receives a face detail pass. Krea runtime memory is released between heavy child generations. Detail failures preserve the usable base panel instead of aborting the sheet.

Automated regression coverage includes dependency management, graph topology, one-job routing, panel geometry, face-only identity references, failure fallback, final persistence, Gallery hiding and isolated imports. Physical likeness/stability acceptance is still pending and must use the same difficult source material that exposed the v1 failure.

Required physical checks remain recorded in the Character Sheet design/plan and PR #4. Do not mark Character Sheet v2 target-accepted until repeated runs, identity quality, BACK correctness, artifact reduction and post-run ordinary Krea Image Edit are all verified on the RX 6950 XT.

## Text-to-SVG v1 — target-accepted on RX 6950 XT

StableAMD has a dedicated **Vector** workspace rather than forcing SVG generation into the normal raster Generate controls.

### Product contract

Text-to-SVG uses the existing Z-Image generation provider for a clean raster source, then a local deterministic vector pipeline:

```text
Vector request
  -> Z-Image raster source
  -> release GPU runtime
  -> optional border-connected background removal
  -> VTracer
  -> Clean SVG sanitizer
  -> resvg_py PNG preview from final sanitized SVG
  -> persisted SVG + preview + Gallery record
```

Vector controls remain intentionally limited to:

- Prompt;
- Style: Icon / Logo mark or Vector Illustration;
- Detail: Simple / Medium / Detailed;
- Colors: Auto / 2 / 4 / 8 / 16;
- Background: Transparent / Solid;
- Solid color when applicable;
- optional Seed.

Sampler, scheduler, LoRA and ControlNet controls are not exposed in the Vector workspace.

### Managed dependency

Pinned local tooling:

```text
VTracer 1.0.0-alpha.4
resvg_py 0.5.0
```

The VTracer ZIP is downloaded only from the allow-listed pinned release, verified by exact expected size + SHA-256, extracted through safe ZIP path checks and promoted atomically with a managed manifest. `resvg_py` is version-pinned. Missing/invalid dependencies disable **Generate SVG** and expose **Install Vectorizer**.

Neither Pillow nor `resvg_py` is imported eagerly by the final StableAMD server.

### Clean SVG security/complexity contract

The final asset is allow-list sanitized before persistence/preview. The sanitizer rejects active or unsupported content including scripts, embedded images, text, external references/URLs, event handlers, DTD/entities and unknown namespaces. Geometry and numeric values are validated and document/path/node complexity is bounded.

VTracer emits a standard root `version="1.1"` attribute. Physical testing exposed that the initial sanitizer rejected this valid metadata marker. The compatibility fix accepts only SVG `1.0` / `1.1` on the input root and strips the attribute from the canonical final Clean SVG; unknown version values remain rejected. The fix is on commit `5782771a9da306e60ec01caaed5fc40a00165825`, with exact-head Actions #871 GREEN: 288 Python tests, 248 Pester tests, package build and artifact upload.

The browser never receives an arbitrary raw SVG document endpoint. `/api/vector/source` returns source as JSON only after all of these are true:

1. path resolves to an existing `.svg` under the managed Vector output root;
2. a matching persisted Gallery history record exists;
3. the record is marked `assetType=svg` and `sanitized=true`;
4. the file still exactly matches its canonical sanitized representation.

Source viewing uses `textContent`, while Download SVG creates a local Blob from that verified source.

### Transparent-background behavior

Transparent mode does not globally delete white pixels. It performs a border-connected flood fill around the inferred edge background. Same-colored pixels enclosed inside the subject therefore remain available to VTracer instead of being erased as holes.

### Physical acceptance evidence — 2026-09-22

The target RX 6950 XT session exercised both agreed v1 product modes:

1. **Icon / Logo mark** — a two-color fox-head prompt with `Simple`, `Colors: 2`, transparent background. The output completed through Z-Image -> VTracer -> sanitizer -> preview, and the first failing attempt recorded a Z-Image prompt execution time of `254.27 s`; the failure was the now-fixed SVG root-version sanitizer mismatch after raster generation.
2. **Vector Illustration** — a fox with three pine trees and crescent moon using `Medium`, `Colors: 8`, transparent background. The result preserved a multi-object layered composition and flat palette with expected raster-to-vector simplification at some fine edges.

The user confirmed all v1 SVG lifecycle actions work on target hardware:

```text
Download SVG: pass
View source:  pass
Reuse:        pass
Delete:       pass
```

This closes the agreed Text-to-SVG v1 physical gate for scope A+B. Additional logo/detail stress samples, repeated complexity measurements and longer provider-regression sessions remain useful non-blocking QA rather than acceptance blockers.
