# StableAMD v0.3 status

Last updated: 2026-09-18

StableAMD v0.3 is the active development line on `feat/stableamd-v0.3` / draft PR #4. The physical acceptance target is an AMD Radeon RX 6950 XT 16 GiB (`gfx1030`) on Windows with the managed TheRock/ROCm + PyTorch + ComfyUI runtime.

The current release line has moved beyond the original SDXL-only scope. The accepted target matrix now includes Z-Image Turbo, Krea 2 Turbo, model-aware LoRA stacks, provider-native editing, structural guidance, curated upscaling, asynchronous generation jobs and the compact product UI.

## Target-accepted baseline

### Core runtime and product shell

Accepted on RX 6950 XT / 16 GiB:

- native Windows AMD execution through the managed TheRock runtime;
- private CPython 3.12.10;
- PyTorch `2.13.0+rocm10.1.0a20260822`;
- torchvision `0.28.0+rocm10.1.0a20260822`;
- torchaudio `2.11.0+rocm10.1.0a20260822`;
- managed loopback compute backend + StableAMD application process;
- persistent Gallery/history and diagnostics;
- clean start/stop ownership through `Start-StableAMD.cmd` / `Stop-StableAMD.cmd`;
- package-first model discovery with external model roots;
- startup loading gate that waits for the initial supported-model catalog before exposing the main GUI;
- asynchronous generation transport (`submit -> poll -> result`) with a long Krea job budget.

Current default 16 GiB runtime policy:

```text
DynamicVRAM + RAM-pressure cache + CPU VAE
```

The CPU-VAE default remains the cross-provider stability safeguard. Provider-local overrides are used only where target-tested, such as GPU VAE selection for the Krea reference/edit path.

### SDXL compatibility baseline

Accepted and maintained:

- txt2img;
- img2img;
- inpaint;
- outpaint;
- sampler/scheduler presets;
- ordered MultiLoRA;
- external checkpoint and LoRA roots;
- Gallery reuse/delete.

SDXL is no longer the main feature-development target.

### Krea 2 LoRA — accepted

The Krea path follows the official model-only adapter topology:

```text
UNETLoader
  -> optional ordered LoraLoaderModelOnly chain
  -> KSampler
```

Target evidence includes successful use of the official `krea2_darkbrush.safetensors` adapter. Qwen3-VL / CLIP remains unchanged; LoRA strength is applied on the diffusion model only.

### Krea OpenPose — accepted

The accepted path uses:

- pinned `ostris/ComfyUI-Krea2-Ostris-Edit`;
- pinned `krea2_turbo_openpose_controlnet.safetensors`;
- `FluxKontextImageScale` for the reference/control image;
- Krea edit model patch semantics;
- curated OpenPose templates and the interactive pose editor;
- safe-frame handling so portrait/landscape pose assets fit the selected Krea generation aspect.

Target testing produced a single correctly posed subject rather than the earlier duplicate-subject failure. Subsequent generations also succeeded with a regular user LoRA enabled together with pose control.

### Krea Depth — accepted

Krea Depth reuses the shared CPU-side Depth Anything V2 Small preprocessor and then applies the provider-specific Control LoRA path from the pinned `facok/comfyui-krea2-controlnet` integration.

The control graph is:

```text
Depth Anything V2 Small
  -> LoadImage
  -> Krea2ControlImageEncode
  -> Krea2ControlLoRALoader
  -> Krea2ControlApply
  -> KSampler
```

Pinned provider assets:

- `facok/comfyui-krea2-controlnet` at commit `79ebfd3bd80d2180b334dd7ce57f3c9ddaa0848f`;
- `Patil/Krea-2-depth-controlnet` / `depth-control-lora.safetensors`;
- exact byte-size and SHA-256 validation before managed installation.

The control image encoder uses grayscale input, per-image min/max normalization, no inversion and latent-size matching. A physical 1024 x 1024 / 8-step / CFG 1 generation completed successfully on the RX 6950 XT with a sensible generated depth preview and an observed runtime of about 147 seconds.

Regular user LoRA + Krea Depth and Image Edit + Depth remain separate future gates; the accepted first route is Krea txt2img + one Depth control source.

### Krea Image Edit — accepted

Whole-image Image Edit was implemented and target-tested successfully on the RX 6950 XT.

The user selects a source image and writes a natural-language instruction such as:

```text
change the jacket to a red leather jacket while keeping the person, pose,
framing and background unchanged
```

The workflow follows the published Krea/Ostris reference-conditioning path:

```text
LoadImage
  -> FluxKontextImageScale
  -> TextEncodeKrea2OstrisEdit
  -> FluxKontextMultiReferenceLatentMethod(index_timestep_zero)
  -> Krea2OstrisEditModelPatch
  -> KSampler
```

Important product behavior:

- the mode is exposed as **Image Edit**, not classic denoise img2img;
- the prompt label changes to **Edit instruction**;
- no denoise slider is shown for Krea Image Edit;
- source dimensions/aspect drive the output latent after `FluxKontextImageScale`;
- normal Krea LoRA remains available;
- the existing asynchronous generation job path is reused;
- Gallery metadata records Image Edit as an edit operation;
- masked Krea editing is not part of this first accepted gate;
- Image Edit + Control guidance remains intentionally blocked until separately designed and target-tested.

GitHub Actions **#660** passed the complete automated suite for this gate: Python API/regression tests, PowerShell/Pester tests, package build and artifact upload. Physical GPU acceptance was then completed on the RX 6950 XT.

## LoRA compatibility — accepted product behavior

StableAMD classifies LoRAs by family rather than exposing every adapter to every provider.

Managed layout:

```text
.runtime/stableamd/models/loras/
├─ shared
├─ sd15
├─ sdxl
├─ sd3
├─ z-image
├─ flux
└─ krea
```

Behavior:

- safetensors metadata is inspected without loading tensors;
- managed folder and filename hints are fallback classifiers;
- known cross-family adapters are rejected server-side;
- unknown adapters remain `unknown` instead of being guessed compatible;
- SDXL applies model + CLIP LoRA strength;
- Z-Image and Krea use model-only LoRA paths;
- ordered stacks are supported where the provider contract allows them.

## Provider dependency installer

The curated dependency pattern is accepted and reused across v0.3 features.

Properties:

- allow-listed HTTPS sources;
- pinned filename/source/license;
- exact expected byte size;
- SHA-256 verification;
- download to temporary managed storage;
- atomic promotion only after verification;
- no silent overwrite of a conflicting file;
- restart/activation through the managed backend lifecycle.

It is used for the accepted Z-Image Union patch, the shared Depth Anything V2 Small preprocessor and provider-specific Krea control/edit dependencies where licensing and source integrity are known.

## Gallery and post-generation tools — accepted

Gallery supports:

- Reuse;
- Delete;
- Upscale;
- Img2Img;
- Inpaint;
- Outpaint.

Provider capabilities remain authoritative. StableAMD reuses the source provider when the requested edit route is supported and otherwise selects a compatible installed editing provider.

Krea now has its own whole-image Image Edit route instead of always falling back to SDXL-style editing.

## Classic upscale — accepted

Stock graph:

```text
LoadImage -> UpscaleModelLoader -> ImageUpscaleWithModel -> SaveImage
```

Accepted curated models:

- RealESRGAN x2plus;
- RealESRGAN x4plus;
- 4x-UltraSharp.

Accepted behavior:

- exact 2x/4x/8x target planner;
- native matching scale preferred;
- shortest compatible x2/x4 chain otherwise;
- intermediate chain images omitted from Gallery;
- manual Gallery Upscale;
- shared Generate `Upscale after`;
- Krea and Z-Image results both pass through the classic provider.

SeedVR2 remains experimental and outside the stable classic upscale path.
