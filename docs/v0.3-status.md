# StableAMD v0.3 status

Last updated: 2026-09-14

StableAMD v0.3 is the active development line on `feat/stableamd-v0.3` / draft PR #4. The target machine is an AMD Radeon RX 6950 XT 16 GiB (`gfx1030`) on Windows using the pinned TheRock/ROCm + PyTorch + ComfyUI stack first accepted in v0.1.

The agreed execution order from this point is recorded in `docs/v0.3-forward-plan.md`: **curated dependency installer -> Krea 2 LoRA -> ControlNet**, followed by first-class image-edit/reference workflows. Inpaint/outpaint stay supported and maintained, but are no longer the main development focus.

## Accepted on the target machine

### Core runtime

- native Windows AMD execution on RX 6950 XT / `gfx1030`;
- private CPython 3.12.10 runtime;
- PyTorch `2.13.0+rocm10.1.0a20260822`;
- torchvision `0.28.0+rocm10.1.0a20260822`;
- torchaudio `2.11.0+rocm10.1.0a20260822`;
- ComfyUI 0.35.0 pinned to `40c4fcdf513a4523e39d54a9d391908af8df8171`;
- managed loopback backend/application lifecycle, persistent history/gallery, live timestamped diagnostics and clean teardown;
- target default launcher profile uses `DisableDynamicVram + LowVram + CacheClassic` without requiring manual flags on every start;
- application and compute backend have separate managed PIDs plus explicit `Start-StableAMD.cmd` / `Stop-StableAMD.cmd` entry points.

A native Windows/ROCm access-violation episode was observed after repeated model/runtime crashes. A full Windows restart cleared the stale lower-level runtime/driver state, after which the current code path passed the full generation matrix again. StableAMD therefore avoids aggressive forced `/free`/model-unload experiments in the proven Z-Image path.

### SDXL

- txt2img;
- img2img;
- inpainting execution;
- outpaint execution through the inpaint provider;
- sampler/scheduler metadata and generation presets;
- ordered MultiLoRA for supported SDXL workflows;
- external checkpoint and LoRA roots.

### Z-Image Turbo

The official three-file ComfyUI package is supported:

- `z_image_turbo_bf16.safetensors`;
- `qwen_3_4b.safetensors`;
- `ae.safetensors`.

The dedicated provider uses the official-style Lumina2/AuraFlow graph and has passed repeated target-machine generation tests.

Recommended RX 6950 XT 16 GiB memory profile:

```powershell
.\Start-StableAMD.cmd
```

The launcher supplies the accepted `DisableDynamicVram + LowVram + CacheClassic` defaults unless explicitly overridden.

Observed warm behavior at the 1024-class / 8-step recommended profile:

- Qwen text encoder stays on CPU;
- Lumina2 is partially resident in GPU memory;
- the proven sampler path remains `res_multistep + simple + CFG 1`;
- cold first generation is substantially slower because model/text-encoder initialization is required.

`HighVram` is not recommended for this 16 GiB card. Z-Image generation profiles include `Small`, `1024`, `1280` and `1536` size tiers plus common portrait/landscape ratios.

Target acceptance includes:

- plain Z-Image Turbo generation;
- one Z-Image LoRA;
- two ordered Z-Image LoRAs in one stack;
- model-only LoRA application through `LoraLoaderModelOnly` (CLIP remains unchanged);
- native Z-Image Inpaint through the Union 2.1 Lite Fun Control patch;
- native Z-Image Outpaint through the same provider-native edit path;
- automatic Outpaint canvas preparation with `256 px` default expansion on left, right, top and bottom;
- Generate `Upscale after` on a Z-Image result;
- Gallery history/reuse/delete after Z-Image and upscale runs.

For lower host-memory pressure StableAMD can also discover the official compact `qwen_3_4b_fp4_mixed.safetensors` and `qwen_3_4b_fp8_mixed.safetensors` encoder variants before falling back to BF16. They are memory-profile options, not prerequisites for the accepted native edit path.

### Krea 2 Turbo

The official FP8 three-file ComfyUI package is accepted on the target RX 6950 XT 16 GiB machine:

- `krea2_turbo_fp8_scaled.safetensors`;
- `qwen3vl_4b_fp8_scaled.safetensors`;
- `qwen_image_vae.safetensors`.

Accepted target behavior:

- package discovery through the normal Models page;
- Krea 2 txt2img through the dedicated `krea2-bundle` provider;
- official-style flat graph with `UNETLoader`, Krea 2 `CLIPLoader`, zeroed negative conditioning, `KSampler`, VAE decode and Gallery persistence;
- conservative 16 GiB profile with Qwen3-VL loaded on CPU;
- `1024 / 8 steps / CFG 1 / Euler / simple` product preset;
- normal Gallery history and reuse metadata;
- classic `Upscale after` works on Krea 2 results.

An initial target run exposed an incomplete/corrupt diffusion safetensors file. StableAMD checks the expected byte sizes of the official Krea 2 package assets during package discovery so a truncated official file is not silently presented as a ready package. The corrected official model then generated successfully on the target machine.

#### Krea 2 LoRA — implemented, target gate pending

The official Comfy-Org Krea 2 Turbo workflow uses optional **`LoraLoaderModelOnly`** adapters. StableAMD now mirrors that path instead of modifying the Qwen3-VL text encoder:

```text
UNETLoader
  -> LoraLoaderModelOnly (optional, ordered stack)
  -> KSampler
```

Implementation state:

- Krea family LoRAs pass the existing model-family compatibility gate;
- ordered stacks are supported up to the product limit of 8;
- model strength is per-entry;
- CLIP strength is fixed to zero / not applied;
- Krea Turbo base defaults stay `8 / CFG 1 / Euler / simple`;
- Gallery history/result metadata persists the Krea LoRA stack for Reuse;
- automated graph/history/model-support tests pass.

This is **not yet target-accepted** until the official style adapter test in `docs/v0.3-krea2-lora-test.md` completes on RX 6950 XT. The first target adapter is `krea2_darkbrush.safetensors` with the official `monochrome ink wash style` trigger.

Krea provider-native general image editing remains a separate future feature and is not inferred from LoRA support.

## Provider-native editing gate — accepted

A real Z-Image native edit path is implemented and accepted on the target RX 6950 XT without changing the accepted Z-Image txt2img/LoRA code path.

Pinned ComfyUI `40c4fcdf513a4523e39d54a9d391908af8df8171` contains:

- `ModelPatchLoader` for `model_patches` assets;
- `ZImageFunControlnet`;
- optional `inpaint_image` and `mask` inputs on that native node.

The first target attempt exposed that node availability alone is not enough. The initially selected `Z-Image-Turbo-Fun-Controlnet-Union.safetensors` is the older control-only model. Its model patch has no additional inpaint input channels (`additional_in_dim == 0`), so the pinned ComfyUI `ZImageControlPatch` returns no encoded inpaint latent and KSampler eventually fails with `AttributeError: 'NoneType' object has no attribute 'to'`.

StableAMD no longer promotes native editing for that old patch. The target dependency is the official inpaint-capable, distilled Lite model:

```text
Z-Image-Turbo-Fun-Controlnet-Union-2.1-lite-2602-8steps.safetensors
```

This is the deliberate RX 6950 XT / 16 GiB choice: about 2.02 GB, 8-step distilled, and Union 2.1 explicitly supports inpainting. Z-Image `inpaint` capability is promoted from `planned` to `supported` dynamically only when ComfyUI exposes this exact patch. If only the old control-only patch is installed, StableAMD keeps editing gated and returns a direct replacement instruction instead of reaching the sampler crash.

Accepted native workflow:

```text
UNETLoader + CLIPLoader(lumina2/cpu) + VAELoader
    -> ModelPatchLoader(Union 2.1 Lite 2602 8-step)
    -> ZImageFunControlnet(inpaint_image + alpha-derived mask)
    -> ModelSamplingAuraFlow(shift 3)
    -> KSampler(denoise 1)
    -> VAEDecode -> SaveImage
```

Outpaint reuses the same native inpaint transport plus the existing source/margin `editContext`. The product prepares the Outpaint canvas automatically with `256 px` on every side by default and shows the real custom canvas size plus long preparation status before sampler progress begins.

Target evidence:

- native Z-Image Inpaint completed successfully;
- native Z-Image Outpaint completed successfully;
- the initially wrong control-only Union patch is rejected before execution;
- the accepted Union 2.1 Lite patch executes through the native Fun Control graph;
- one Outpaint run failed before sampling with Windows `os error 1455` (`The paging file is too small for this operation to complete`) while loading the BF16 diffusion model after the CPU text encoder had loaded;
- a full Windows reboot cleared that host-memory/commit-pressure state and the same Outpaint path then completed successfully.

The target edit gate is complete. LoRA + native Z-Image edit composition remains a later optional follow-up, not a blocker for the current plan.

## Curated provider dependency installer

The first reusable provider-dependency installer is implemented for the accepted Z-Image Union 2.1 Lite patch.

Catalog:

```text
config/model-patches.v0.3.json
```

Behavior:

- pins official URL, exact byte size, SHA-256, license and source homepage;
- downloads only from allow-listed HTTPS source hosts;
- streams to a temporary file under `.runtime/stableamd/models/model_patches`;
- verifies exact size and SHA-256 before atomic promotion;
- never silently overwrites a conflicting/corrupt file;
- Models page exposes `Not installed`, `Restart required`, `Ready` and invalid-file states;
- `Install & activate` restarts only the managed compute backend, leaving the StableAMD application process running;
- capability/model state is refreshed after activation.

The same installer pattern is intended for future ControlNet/model-patch dependencies rather than adding manual download commands for each feature.

## LoRA compatibility

StableAMD treats LoRA compatibility as model-family-aware metadata instead of assuming that every discovered adapter can be used everywhere.

- managed LoRA folders are grouped by family (`shared`, `sd15`, `sdxl`, `sd3`, `z-image`, `flux`, `krea`);
- safetensors metadata is inspected without loading tensor payloads;
- fallback classification uses managed folder and then filename hints;
- known cross-family mismatches are blocked server-side;
- unknown adapters remain explicitly `unknown` instead of being guessed compatible;
- the UI hides incompatible adapters by default and can show them for inspection;
- SDXL supports model + CLIP LoRA strengths;
- Z-Image uses model-only LoRAs and ignores CLIP strength by design;
- Krea 2 now uses the official model-only LoRA pattern and is pending target acceptance;
- SDXL, Z-Image and the implemented Krea 2 path support ordered stacks up to the product limit of 8 entries.

## Generate UI compactness pass

Accepted on the target desktop flow.

- generation mode, model and preset are grouped before the prompt;
- model-aware Size and Ratio controls stay compact;
- manual Width/Height are shown only for Custom size;
- Seed, Sampler, Scheduler, Steps and CFG share one dense row;
- Negative prompt is retained for SDXL and hidden for model families whose workflow does not use it, including Z-Image and Krea 2;
- LoRA stack is the primary adapter UI;
- one visible Strength value controls model + CLIP by default where supported, with per-LoRA CLIP override available only when relevant;
- Z-Image is explicitly diffusion-model-only; Krea 2 backend likewise ignores CLIP because the official path is model-only;
- generation mode choices are hidden until the selected model capability data is known, so planned modes are not advertised as usable;
- compact icon-led actions are used in Gallery without making the UI icon-only.

The compact layer rearranges existing controls rather than replacing the proven provider APIs.

## Gallery and post-generation tools

Gallery items expose:

- Upscale;
- Img2Img;
- Inpaint;
- Outpaint;
- Delete.

Accepted behavior:

- Gallery reads history directly in Python and skips individual malformed records instead of failing the whole refresh;
- current and legacy PascalCase history records can be deleted;
- Img2Img/Inpaint/Outpaint first try to reuse the exact model that generated the source image when that provider declares the requested capability;
- if the source model cannot edit, StableAMD selects an installed compatible editing provider (currently SDXL for the proven fallback edit path);
- the source prompt is restored automatically for editing handoffs;
- Outpaint preserves source prompt/image relationship and asymmetric margins in history;
- Z-Image Outpaint defaults to `256 px` on every edge, prepares the expanded canvas automatically, switches to the actual Custom size and blocks duplicate starts while generation is active;
- Upscale records are labelled as upscale operations instead of `Unknown model`.

### Outpaint quality note

Current SDXL outpaint uses a blurred source continuation plus a soft `Blend overlap`. Target testing shows that full denoise (`1.0`) reliably replaces the previous gray expansion field, while `0.9` / `0.95` can still leave a gray strip. A visible sharpness/seam transition can remain around the preserved source image, and increasing the overlap from 64 px to 128 px did not materially remove it. Final feather/compositing work is deferred while higher-priority provider work progresses.

Provider capability truth remains authoritative. Krea-generated images still fall back to a compatible editor. Z-Image-generated images use native Z-Image inpaint/outpaint only when the inpaint-capable Union 2.1 Lite patch is installed and exposed by ComfyUI; otherwise the existing compatible-provider fallback is preserved.

## Classic upscale

The classic provider uses stock ComfyUI nodes:

```text
LoadImage -> UpscaleModelLoader -> ImageUpscaleWithModel -> SaveImage
```

Managed root:

```text
.runtime/stableamd/models/upscale_models
```

Target evidence accepted:

- ComfyUI discovers `RealESRGAN_x2plus.pth` correctly;
- StableAMD handles the current `COMBO` + `options` object-info contract;
- the workflow `RepoRoot` mismatch is fixed;
- RealESRGAN x2 completed end-to-end on the target RX 6950 XT;
- curated native x4 upscale works on the target machine;
- Krea 2 output can be passed through the same upscale-after path successfully;
- upscale history stores provider/model/scale metadata;
- Generate upscale-after and Gallery manual upscale both execute successfully on the target machine.

### Exact 2x / 4x / 8x planner

StableAMD treats `2x`, `4x` and `8x` as requested final factors rather than blindly exposing a model's native scale.

- a native matching model is preferred when available;
- otherwise the shortest exact chain is used;
- with only `RealESRGAN_x2plus`, 4x becomes `2x -> 2x` and 8x becomes `2x -> 2x -> 2x`;
- with x4 and x2 models installed, 8x can use a two-pass `4x * 2x` chain;
- impossible exact combinations are rejected before execution;
- intermediate chain images are not added to Gallery history;
- Gallery manual Upscale has Target `2x / 4x / 8x` plus `Auto` or an explicit preferred model;
- Generate has a shared `Upscale after` control for txt2img/img2img/inpaint/outpaint with `Off / 2x / 4x / 8x`;
- the Generate UI previews target dimensions and warns for unusually large outputs.

### Curated one-click classic upscalers

Accepted on the target machine:

- `RealESRGAN x2plus` — native 2x, BSD-3-Clause;
- `RealESRGAN x4plus` — native 4x, BSD-3-Clause;
- `4x-UltraSharp` safetensors — native 4x, CC BY-NC-SA 4.0 / non-commercial.

The application does not accept arbitrary download URLs from the browser. The curated catalog pins the source URL, expected byte size and SHA-256. Downloads are streamed into a temporary managed file, size/checksum verified, then atomically promoted into `.runtime/stableamd/models/upscale_models`. Existing conflicting files are not overwritten silently.

The Gallery Upscale dialog exposes `Install & activate`. After a successful verified download it can restart only the managed compute backend so ComfyUI registers the model while the StableAMD application remains running. UltraSharp is clearly marked as non-commercial in the UI.

SeedVR2 remains a separate optional/experimental provider and is not part of this classic chaining logic.
