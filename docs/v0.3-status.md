# StableAMD v0.3 status

Last updated: 2026-09-21

StableAMD v0.3 is the active development line on `feat/stableamd-v0.3` / draft PR #4. The physical acceptance target remains Windows + AMD Radeon RX 6950 XT 16 GiB (`gfx1030`) with the managed TheRock/ROCm + PyTorch + ComfyUI runtime.

The product now combines the accepted Radeon runtime with SDXL compatibility, Z-Image Turbo, Krea 2 Turbo, ordered/provider-aware LoRA stacks, provider-native editing, structural guidance, automatic DWPose extraction, curated upscaling, async generation jobs, Gallery/history and the compact StableAMD UI.

## Target-accepted baseline

### Core runtime

Accepted on RX 6950 XT / 16 GiB:

- native Windows AMD execution through the managed TheRock runtime;
- private CPython 3.12.10;
- PyTorch `2.13.0+rocm10.1.0a20260822`;
- torchvision `0.28.0+rocm10.1.0a20260822`;
- torchaudio `2.11.0+rocm10.1.0a20260822`;
- managed loopback ComfyUI + StableAMD application process;
- startup loading gate, Gallery/history and diagnostics;
- async generation transport (`submit -> poll -> result`);
- package-first model discovery with external model roots.

Default 16 GiB stability policy remains:

```text
DynamicVRAM + RAM-pressure cache + CPU VAE
```

Provider-local overrides are used only where target-tested.

### SDXL compatibility

Accepted and maintained: txt2img, img2img, inpaint, outpaint, sampler/scheduler presets, ordered MultiLoRA, external model roots and Gallery reuse/delete. SDXL is no longer the main feature-development target.

## Z-Image Turbo — accepted

Accepted target behavior includes repeated txt2img, model-only LoRA stacks, native inpaint/outpaint with the accepted Union 2.1 Lite Fun Control patch, Canny, OpenPose-map and Depth control, Gallery persistence and shared post-generation upscaling.

### Krea Image Edit — accepted

Published reference-conditioning route:

```text
LoadImage
  -> FluxKontextImageScale
  -> TextEncodeKrea2OstrisEdit
  -> FluxKontextMultiReferenceLatentMethod(index_timestep_zero)
  -> Krea2OstrisEditModelPatch
  -> KSampler
```

Image Edit exposes natural-language whole-image editing rather than classic denoise img2img. It supports material/texture replacement and up to two extra content/style/material references. Masked Krea editing and Image Edit + Control remain deferred.

## Character Sheet v1 — visual acceptance failed

The first Character Sheet implementation used five independent Krea Image Edit renders, then a local `grid-3x2` composite. It was functionally stable, but physical testing exposed unacceptable visual behavior on the known reference photograph:

- generated faces only loosely resembled the source person;
- background/statue information leaked into generated views;
- repeated per-view generation accumulated identity drift and visible artifacts;
- the later FACE-anchor refinement improved the architecture but did not make identity consistency reliable enough for acceptance.

The sequential/anchor implementation is therefore retained only as the explicit `legacy-sequential` comparison path during v0.3 acceptance. It is not the default Character Sheet workflow and is not target-accepted.

## Character Sheet v2 — implemented, automated GREEN, physical acceptance pending

Character Sheet now defaults to a training-matched **Krea 2 Identity Edit v1.2** pipeline instead of the heuristic sequential flow.

Pinned dependency:

```text
node pack: lbouaraba/comfyui-krea2edit
commit:    86f886dac23013d88996e3a2e99093ba44d322fb
LoRA:      krea2_identity_edit_v1_2.safetensors
SHA-256:   6adf9a69cc9502d286db7b69964d37da7e9cfe4b05b4d004bc275f087d3fd3cf
```

StableAMD exposes dependency status and a controlled install action. Missing nodes/LoRA never silently fall back to v1; v2 stays unavailable until the pinned dependency is visible after any required restart.

### Training-matched base graph

The v2 Identity Edit graph uses:

```text
Krea 2 Turbo model
  -> LoraLoaderModelOnly (Identity Edit v1.2, strength 1.0)
  -> Krea2EditModelPatch
  -> Krea2EditGroundedEncode
  -> KSampler
```

Server-owned acceptance settings:

- base target: `1792 x 1024` (below the 2 MP Identity Edit ceiling and divisible by 16);
- `fit_mode = fit`;
- `ref_boost = 4.0`;
- `grounding_px = 1024`;
- `10 steps / CFG 1 / Euler / simple / denoise 1`;
- `target_latent` explicitly wired to `Krea2EditModelPatch`.

The source image is conditioned once to generate one five-panel base sheet:

```text
FACE | FRONT | 3/4 | SIDE | BACK
```

This removes the v1 pattern of creating five unrelated base generations and asking prompt wording/shared seed to hold identity together.

### Local panel/detail pipeline

After the base job completes, StableAMD releases Krea runtime memory, then locally splits the sheet into five horizontal logical regions. A small edge inset prevents panel boundaries from entering face analysis.

FACE, FRONT, 3/4 and SIDE can run an optional serial detail pass:

1. DWPose searches the generated panel for a usable face/head region;
2. the face box expands to include hair/head context and is aligned to 16 px;
3. image A is the generated head crop, preserving that panel's camera/head orientation;
4. image B is the tight identity crop from the original source;
5. the same Identity Edit v1.2 graph corrects identity/fine head detail;
6. the corrected crop is blended back with a soft 12% feather mask.

SIDE receives an explicit strict-profile constraint. BACK never runs face detection or a face detail generation, preventing an accidental portrait from being inserted into the rear view.

Failure semantics are deliberately non-fatal for detail children:

- no detected face -> keep the base panel and record `detailerSkipped=no-face`;
- malformed face region -> keep the base panel;
- detail generation failure -> keep the base panel and record `detailerSkipped=generation-failed`;
- BACK -> keep unchanged and record `detailerSkipped=back-view`.

Krea `/free` is called after the base job and after every attempted detail job. There are no parallel Krea generations in v2.

### Final asset / Gallery contract

The corrected/original panels are reassembled at the original `1792 x 1024` size and persisted as one final Character Sheet history record. The result records per-panel detail status plus the exact Identity Edit version/settings.

Only after final image/history persistence succeeds does StableAMD hide the base/detailer child history from the default Gallery. If final persistence fails, intermediates remain visible for diagnostics instead of being lost.

### Frontend contract

The Character Sheet UI now shows **Character Sheet v2 · Identity Edit** by default and provides:

- optional **Character description** field;
- dependency readiness/install status;
- `Install Identity Edit` when needed;
- restart-required status after installation;
- backend-owned geometry (global Width/Height hidden for v2);
- one async Character Sheet request instead of the old five/eight-job browser orchestration;
- progress fallback for Base sheet / Face detail / Final compose;
- final result summary with per-panel detail completed/skipped state;
- advanced `legacy-sequential` selector for comparison during v0.3 acceptance.

### Physical RX 6950 XT acceptance checklist

Do not mark Character Sheet v2 target-accepted until all are true:

```text
[ ] full base + detailer + final compose completes
[ ] source person is recognizably the same in FACE / FRONT / 3/4 / SIDE
[ ] BACK has no inserted face/portrait
[ ] statue/background leakage and ghost/grid/debris artifacts are materially reduced
[ ] final Gallery shows one Character Sheet card by default
[ ] detailer skips/failures preserve usable base panels
[ ] a second consecutive v2 run completes
[ ] ordinary Krea Image Edit works immediately after v2
[ ] no 16 GiB runtime instability appears across the repeated pass
```

The same source photographs that exposed the v1 failure should be used first so the comparison is meaningful.

## LoRA/dependency product behavior

StableAMD classifies LoRAs by provider/model family and rejects known cross-family adapters. Curated dependencies use allow-listed HTTPS sources, pinned source/revision/license, exact size/SHA-256 verification, temporary download + atomic promotion and actionable restart state. Character Sheet v2 reuses this managed dependency pattern.

## Gallery and upscale — accepted

Gallery supports Reuse, Delete, Upscale, Img2Img, Inpaint and Outpaint according to provider capability. RealESRGAN x2/x4 and 4x-UltraSharp remain curated/accepted, including exact 2x/4x/8x planning.
