# StableAMD v0.3 status

Last updated: 2026-09-20

StableAMD v0.3 is the active development line on `feat/stableamd-v0.3` / draft PR #4. The physical acceptance target is an AMD Radeon RX 6950 XT 16 GiB (`gfx1030`) on Windows with the managed TheRock/ROCm + PyTorch + ComfyUI runtime.

The release line has moved beyond the original SDXL-only scope. The product now combines an accepted Radeon runtime with Z-Image Turbo, Krea 2 Turbo, model-aware LoRA stacks, provider-native editing, structural guidance, automatic pose extraction, curated upscaling, asynchronous generation jobs and the compact product UI.

## Target-accepted baseline

### Core runtime and product shell

Accepted on RX 6950 XT / 16 GiB:

- native Windows AMD execution through the managed TheRock runtime;
- private CPython 3.12.10;
- PyTorch `2.13.0+rocm10.1.0a20260822`;
- torchvision `0.28.0+rocm10.1.0a20260822`;
- torchaudio `2.11.0+rocm10.1.0a20260822`;
- managed loopback compute backend + StableAMD application process;
- persistent Gallery/history and diagnostics;
- clean start/stop ownership through `Start-StableAMD.cmd` / `Stop-StableAMD.cmd`;
- package-first model discovery with external model roots;
- startup loading gate that waits for the initial supported-model catalog before exposing the main GUI;
- asynchronous generation transport (`submit -> poll -> result`) with a long Krea job budget.

Current default 16 GiB runtime policy:

```text
DynamicVRAM + RAM-pressure cache + CPU VAE
```

The CPU-VAE default remains the cross-provider stability safeguard. Provider-local overrides are used only where target-tested, including GPU VAE selection for the Krea reference/edit path.

### SDXL compatibility baseline

### Krea LoRA — accepted

The Krea path follows the official model-only adapter topology:

```text
UNETLoader
  -> optional ordered LoraLoaderModelOnly chain
  -> KSampler
```

The official `krea2_darkbrush.safetensors` adapter passed target testing. Qwen3-VL / CLIP remains unchanged; LoRA strength is applied on the diffusion model only.

### Krea OpenPose — accepted

The accepted path uses the pinned Krea/Ostris edit integration plus the Krea 2 Turbo pose adapter, safe-frame handling, curated pose templates and the interactive pose editor. The physical target produced one correctly posed subject and also passed a normal user LoRA + OpenPose combination.

### Krea Depth — accepted

Krea Depth reuses the shared CPU-side Depth Anything V2 Small preprocessor and provider-specific Krea 2 Control LoRA route. A physical 1024 x 1024 / 8-step / CFG 1 generation completed successfully on the RX 6950 XT with a sensible depth preview.

Regular user LoRA + Krea Depth remains a separate future acceptance gate.

### Automatic DWPose extraction — accepted

Automatic extraction from a normal photograph is implemented and physically target-tested. StableAMD can produce multi-person body + hands + face pose output and feed that result into the existing OpenPose workflow. This same managed DWPose runtime is now reused by Character Sheet Auto framing for human subject detection.

### Krea Image Edit — accepted

Whole-image Image Edit was target-tested successfully on the RX 6950 XT.

Published reference-conditioning route:

```text
LoadImage
  -> FluxKontextImageScale
  -> TextEncodeKrea2OstrisEdit
  -> FluxKontextMultiReferenceLatentMethod(index_timestep_zero)
  -> Krea2OstrisEditModelPatch
  -> KSampler
```

Product behavior:

- mode is exposed as **Image Edit**, not classic denoise img2img;
- prompt label becomes **Edit instruction**;
- no denoise slider;
- normal Image Edit follows source dimensions/aspect after `FluxKontextImageScale`;
- regular Krea LoRA remains available;
- asynchronous generation transport is reused;
- Gallery records the edit operation;
- masked Krea editing remains deferred;
- Image Edit + Control remains blocked until separately designed and target-tested.

## Krea editing extensions — implemented

### Material / texture replacement

StableAMD exposes a focused task for replacing surface/material appearance while asking Krea to preserve object geometry, lighting, composition and unrelated areas. Built-in material presets plus custom material descriptions are available.

### One/two-image references

Image Edit supports up to two additional references with explicit roles:

- style;
- material;
- content.

The source remains Picture 1; extra images are passed as Picture 2 / Picture 3 through the same Krea reference-conditioning graph. Request size limits and Gallery metadata were extended accordingly.

## Character Sheet — implemented, physical quality acceptance pending

The original single-pass four-view `Character turnaround` experiment remains only as a legacy backend compatibility path. The product UI now exposes **Character Sheet**.

The first Character Sheet implementation generated five separate `1024 x 1024` images and displayed them as a frontend-only grid. Physical testing exposed two quality/product problems:

- a landscape portrait source could spend too much reference area on empty background while every generated view was forced into a square;
- the five child generations appeared as five separate Gallery cards and there was no persisted one-image sheet.

The current quality implementation addresses both.

### Sequential generation

StableAMD renders five independent Krea Image Edit jobs:

1. Face close-up;
2. Front;
3. 3/4;
4. Side;
5. Back.

Each view therefore gets a full generation instead of asking one diffusion pass to draw several copies of the character at once.

### Framing and source preprocessing

The UI exposes:

- **Auto** — default;
- **Portrait**;
- **Full body**.

For a detected human source, Auto reuses the managed DWPose runtime once per source and derives a subject bounding box from keypoints. It distinguishes portrait vs full-body using body visibility, creates a subject-focused reference crop, and gives Face a tighter face/head reference crop. Cropping changes framing only; the source is never stretched to a different aspect ratio.

If the source is not recognized by DWPose — important for stylized/non-human characters — StableAMD preserves the source framing/aspect instead of applying an unsafe human center crop.

### View-specific size and prompt contract

- Face close-up: `1024 x 1024`;
- Portrait Front / 3/4 / Side / Back: `896 x 1152`;
- Full-body Front / 3/4 / Side / Back: `832 x 1216`;
- unrecognized Auto fallback: approximately 1 MP while preserving source aspect, aligned to 16 px.

Prompts are framing-aware. Portrait views request an upper-body composition and no longer contradict the source with `head to toe`; Full body retains explicit head-to-toe wording; unknown-source fallback asks for approximately the same visible-body coverage as Picture 1.

### Persisted final sheet

After all five views succeed, StableAMD creates a sixth **asset**, but not a sixth AI generation. Pillow composes the already-generated images into one local PNG:

```text
FACE | FRONT | 3/4
     SIDE | BACK
```

The layout is `grid-3x2`, with Side/Back centered on row two and labels rendered outside the generated image areas. Child images use contain-style fitting so their aspect ratios are preserved.

The final composite is a normal StableAMD output/history record and is the card intended for the main Gallery. Only after the composite succeeds are child records marked `galleryHidden=true` and linked to the parent PromptId/ImagePath. This keeps the five source views traceable without flooding the default Gallery.

### Acceptance state

**Implementation and automated contract work are complete; physical quality acceptance on the RX 6950 XT is still pending.**

The target pass must validate:

- Auto crop on the known landscape portrait test source;
- identity quality in Face / Front / 3/4 / Side / Back;
- correct profile/rear semantics for Side and Back;
- Portrait vs Full body override behavior;
- safe fallback for non-human/unrecognized characters;
- persisted `grid-3x2` composite and one-card Gallery behavior;
- normal Krea Image Edit after a complete sheet;
- repeated runs without 16 GiB runtime instability.

Do not mark Character Sheet `target-accepted` until that physical pass is complete.

## LoRA compatibility — accepted product behavior

StableAMD classifies LoRAs by family rather than exposing every adapter to every provider.

Managed layout:

```text
.runtime/stableamd/models/loras/
├─ shared
├─ sd15
├─ sdxl
├─ sd3
├─ z-image
├─ flux
└─ krea
```

Known cross-family adapters are rejected server-side, unknown adapters remain `unknown`, SDXL applies model + CLIP strength, and Z-Image/Krea use model-only paths.

## Provider dependency installer

The curated dependency pattern remains accepted:

- allow-listed HTTPS sources;
- pinned source/revision/license;
- exact expected byte size;
- SHA-256 verification;
- temporary download + atomic promotion;
- no silent overwrite of conflicting files;
- managed restart/activation.

It is reused across the accepted Union patch, Depth Anything V2 Small and Krea control/edit dependencies.

## Current verification state

Automated CI remains the gate for parsing, Python API/regression tests, Pester/unit regression tests, package build and artifact upload. Physical GPU/runtime acceptance is always separate and must be completed on the RX 6950 XT before a new provider/quality route is called target-accepted.
