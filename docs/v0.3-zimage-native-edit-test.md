# StableAMD v0.3 — Z-Image native edit target test

This gate validates provider-native Z-Image inpaint/outpaint on the accepted RX 6950 XT / Windows stack without changing the proven Z-Image txt2img + LoRA path.

## Why this path is real

The pinned ComfyUI commit `40c4fcdf513a4523e39d54a9d391908af8df8171` contains the native `ModelPatchLoader` and `ZImageFunControlnet` nodes. `ZImageFunControlnet` accepts `inpaint_image` plus `mask`, so StableAMD can use the same PNG-alpha inpaint transport already used by the Gallery editor.

A first target test exposed an important dependency detail: the original `Z-Image-Turbo-Fun-Controlnet-Union.safetensors` is a control-only patch. The node exposes inpaint-shaped inputs generically, but that older model reports no additional inpaint channels. In the pinned ComfyUI implementation this leaves the encoded inpaint control latent as `None`, and sampling fails with `AttributeError: 'NoneType' object has no attribute 'to'` inside `ZImageControlPatch`.

StableAMD therefore no longer treats the original Union patch as an inpaint dependency. Native editing is unlocked only for the official Union 2.1 inpaint-capable target below.

Krea 2 stays capability-gated for editing: the pinned local Krea 2 Turbo path does not currently expose an equivalent validated local edit workflow.

For the RX 6950 XT 16 GiB target use the official Alibaba PAI distilled Lite patch:

- repository: `alibaba-pai/Z-Image-Turbo-Fun-Controlnet-Union-2.1`
- file: `Z-Image-Turbo-Fun-Controlnet-Union-2.1-lite-2602-8steps.safetensors`

- size: `2016627488` bytes

StableAMD managed destination:

.runtime/stableamd/models/model_patches/Z-Image-Turbo-Fun-Controlnet-Union-2.1-lite-2602-8steps.safetensors
```

Official download URL:

```

The Lite model is intentional for the 16 GiB Radeon target. It is roughly 2.02 GB, is distilled for the same 8-step cadence already accepted for Z-Image Turbo, and the Union 2.1 family explicitly supports inpainting.

The old file may be deleted to avoid confusion:

```powershell
Remove-Item ".runtime\stableamd\models\model_patches\Z-Image-Turbo-Fun-Controlnet-Union.safetensors" -ErrorAction SilentlyContinue
```

After the new file is present, restart StableAMD completely so ComfyUI refreshes `ModelPatchLoader` choices.

## Capability behavior

StableAMD does **not** statically advertise Z-Image inpaint. On `/api/model-support`, `inpaint` changes from `planned` to `supported` only when ComfyUI actually exposes the exact inpaint-capable Union 2.1 Lite target.

The older control-only Union file no longer unlocks the capability. If it is the only patch installed, the edit layer stays gated and reports a direct replacement instruction instead of reaching KSampler and crashing.

That means Gallery Inpaint/Outpaint can keep the original Z-Image model only when the native edit dependency is genuinely available. If the patch is absent, the existing capability-driven fallback remains unchanged.

## First target test

1. Start StableAMD normally with the accepted default RX 6950 XT profile.
2. Confirm ordinary Z-Image txt2img still works before editing.
3. Generate a simple Z-Image source at 1024-class resolution.
4. From Gallery choose **Inpaint**, paint one clearly bounded object/region, keep LoRA disabled and generate with a detailed replacement prompt.
5. From the same source choose **Outpaint**, use a modest expansion and generate once.
6. Run another ordinary Z-Image txt2img afterwards to prove the edit provider did not destabilize the accepted base path.

The first native edit workflow deliberately uses:

- base Z-Image Turbo three-file bundle;
- `ModelPatchLoader` with the Union 2.1 Lite 2602 8-step patch;
- `ZImageFunControlnet` with the source RGB image and PNG-alpha mask;
- `ModelSamplingAuraFlow` shift `3.0`;
- `8 steps / CFG 1 / res_multistep / simple` unless the request explicitly carries another accepted Z-Image setting;
- edit denoise fixed to `1.0` for the initial target gate;
- control strength `1.0` (Union 2.1 documentation recommends a relatively strong control scale for inpainting continuity);
- no LoRA during the first native-edit acceptance run.

Outpaint reuses the same native inpaint path plus the existing `editContext` source/margin metadata.

## Acceptance evidence to capture

- result image for one inpaint and one outpaint;
- the backend log around `ModelPatchLoader` / `ZImageFunControlnet` execution;
- whether the untouched region remains acceptably stable;
- whether the following normal Z-Image txt2img still succeeds;
- approximate generation time and any VRAM/runtime warnings.

Do not mark Z-Image native editing accepted until those target-machine checks pass.
