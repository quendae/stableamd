# StableAMD v0.1 validation

This document separates what has already been proven on the RX 6950 XT from what still has to be run as the final packaged product acceptance pass.

## Proven foundation

The feasibility spike already proved native Windows GPU generation on **AMD Radeon RX 6950 XT 16 GiB (`gfx1030`)** through the TheRock multi-arch runtime, PyTorch ROCm and ComfyUI.

Validated reference stack:

- GPU: AMD Radeon RX 6950 XT 16 GiB;
- target: `gfx1030` / `device-gfx1030`;
- Python for the product bootstrap: `3.12.10`;
- PyTorch: `2.13.0+rocm10.1.0a20260822`;
- torchvision: `0.28.0+rocm10.1.0a20260822`;
- torchaudio: `2.11.0+rocm10.1.0a20260822`;
- ComfyUI: `0.35.0`, commit `40c4fcdf513a4523e39d54a9d391908af8df8171`;
- reference model: Stable Diffusion XL 1.0 base;
- generation: `1024x1024`, 20 steps, batch 1;
- observed generation time: about 102 seconds;
- observed peak VRAM: about 14 GiB.

The tested TheRock package source is `https://rocm.nightlies.amd.com/whl-multi-arch/`. The machine-readable release lock is `config/runtime-lock.v0.1.json`.

## Automated acceptance

The GitHub Actions suite covers all non-GPU contracts:

- PowerShell syntax and Python helper compilation;
- StableAMD application API tests;
- runtime lifecycle contracts;
- deterministic runtime bootstrap plan with exact package versions;
- model discovery/import/download contracts;
- SDXL workflow and history contracts;
- frontend/API integration contracts;
- one-click launcher contracts;
- release packaging contract;
- a real plan-only build of a clean package copy with no runtime downloads.

The release package is source-only by design. It must not contain `.runtime/`, models, generated images, diagnostics, tests, or Git metadata.

## Runtime bootstrap design

When a runtime is missing, `scripts/Install-StableAMDRuntime.ps1` now:

1. reads only the versions in `config/runtime-lock.v0.1.json`;
2. detects the supported `gfx1030` Radeon target before the large download;
3. downloads a private Python 3.12.10 installer and validates its Authenticode signer;
4. installs exact TheRock torch / torchvision / torchaudio versions for `device-gfx1030`;
5. downloads ComfyUI by immutable commit instead of following a moving branch/tag at install time;
6. installs ComfyUI dependencies from the locked source while removing the generic torch-family lines, preventing PyPI from replacing the AMD packages;
7. imports torch, torchvision and torchaudio;
8. runs the same real FP16 Radeon compute probe used during the spike;
9. writes `.runtime/stableamd/runtime-install.json` only after compute validation passes.

`Launch-StableAMD.ps1` invokes this bootstrap automatically only when the required managed Python/ComfyUI runtime is missing or incomplete. Existing runtimes are reused rather than overwritten.

## Clean-package runtime acceptance

The bootstrap implementation is complete in code, but target-machine execution remains **pending**. Test it without touching the development runtime by running:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\Test-StableAMDPackage.ps1
```

The harness:

- builds a new source-only package under `diagnostics\acceptance-package-*`;
- uses separate local backend/application ports;
- installs a fresh private runtime inside that package copy;
- performs the real FP16 GPU gate;
- launches the packaged managed backend and StableAMD application;
- verifies `/api/health`, managed backend status and model API access;
- writes `diagnostics\acceptance-package-<timestamp>.json`;
- stops the isolated processes;
- removes the successful isolated runtime by default, while keeping failed runs for diagnosis.

Use `-KeepRuntime` if the successful isolated runtime should be retained. To inspect the exact plan with no runtime download, use:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\Test-StableAMDPackage.ps1 -PlanOnly
```

## Final RX 6950 XT product acceptance

The following checks are required on the actual Radeon machine before calling v0.1 hardware-accepted:

- [ ] **clean-package runtime install — pending**. Run `Test-StableAMDPackage.ps1` and obtain `status: passed` without hand-editing Python packages or environment variables.
- [ ] Start the normal development/package copy with `Start-StableAMD.cmd` and confirm the application opens on loopback only.
- [ ] Confirm Diagnostics identifies RX 6950 XT / `gfx1030` and reports a healthy managed backend.
- [ ] Confirm `scripts/Get-StableAMDStatus.ps1` reports the managed backend as running and exposes the Radeon device.
- [ ] Import a valid SDXL `.safetensors` checkpoint through Models and confirm it appears in the model list.
- [ ] Download or register a Hugging Face checkpoint through the product model flow and verify structural validation.
- [ ] Generate one default SDXL image through the StableAMD Generate page at `1024x1024`, 20 steps, batch 1, without opening the ComfyUI node UI.
- [ ] Confirm the generated image appears in Gallery with prompt, model, dimensions, seed and settings metadata.
- [ ] Exercise Settings and Diagnostics and confirm failures are reported as product-level messages rather than raw node errors.
- [ ] Stop the managed backend with `scripts/Stop-StableAMD.ps1` and verify only the recorded StableAMD process is stopped.
- [ ] Relaunch and confirm an existing healthy service can be reused safely.

## Release package check

From the repository root:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\Build-StableAMDPackage.ps1
```

Expected outputs:

```text
dist\StableAMD-0.1.0\
dist\StableAMD-0.1.0.zip
```

The ZIP intentionally does **not** bundle the multi-gigabyte ROCm/PyTorch runtime or model checkpoints. First launch installs the pinned runtime when it is absent. The target-machine clean-package run is still marked **pending** until the new bootstrap is exercised end-to-end on the RX 6950 XT.

## Release decision

v0.1 can be called hardware-accepted only when the automated suite is green and every item in the final RX 6950 XT product acceptance section has been run successfully on the target machine. The earlier feasibility generation proves the compute stack is viable; the clean-package harness now verifies whether the packaged installer reproduces that stack without relying on the previous development runtime.
