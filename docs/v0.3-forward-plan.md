# StableAMD v0.3 forward plan

Last updated: 2026-09-16

This is the execution order after the accepted native Z-Image edit path, target-accepted Krea 2 LoRA/OpenPose path and target-accepted Krea 2 whole-image Image Edit.

## Accepted baseline

- Native Windows AMD runtime lifecycle is accepted on RX 6950 XT / 16 GiB.
- SDXL txt2img/img2img/inpaint/outpaint and ordered MultiLoRA are accepted, but SDXL is no longer the feature-development priority.
- Z-Image Turbo txt2img + ordered model-only LoRA is accepted.
- Z-Image native inpaint/outpaint is accepted with Union 2.1 Lite 2602 8-step.
- Krea 2 Turbo FP8 txt2img is accepted.
- Krea 2 model-only LoRA is target-accepted.
- Krea 2 OpenPose is target-accepted, including coexistence with a normal user LoRA.
- Krea 2 whole-image Image Edit is target-accepted.
- RealESRGAN / curated upscale and Gallery reuse remain accepted.
- Long generation requests use the async `submit -> poll -> result` transport.

## Immediate execution: remaining structural guidance

Control work remains provider-first for **Z-Image Turbo and Krea 2 Turbo**. **SDXL is deferred** unless required as a compatibility fallback.

### Z-Image Turbo

Use the already accepted Alibaba PAI **Z-Image Fun ControlNet Union 2.1 Lite** patch where practical rather than adding unnecessary large control dependencies.

Current priorities:

1. finish target acceptance for the prepared Z-Image control routes already implemented;
2. select/pin a lightweight depth preprocessor suitable for the managed Windows/AMD runtime;
3. improve pose handling only after the concrete preprocessor/control route is proven on target hardware.

Every route remains capability-gated. A graph existing in code is not enough to advertise it as accepted.

### Krea 2 Turbo

The first structural route is complete:

- **OpenPose map** — accepted on RX 6950 XT;
- pinned Krea/Ostris edit integration;
- pinned Turbo pose adapter;
- curated pose templates and interactive editor;
- safe-frame handling;
- user LoRA coexistence verified.

Next Krea control work:

1. **Depth** — evaluate/pin a Turbo-compatible, redistributable path plus a suitable local depth preprocessor.
2. **Canny** — keep gated until a Krea 2 Turbo-specific route is demonstrated; do not treat unrelated NK2E/public Canny examples as equivalent without target proof.
3. **Automatic pose extraction** — derive OpenPose/DWPose from a normal photo so users do not need an external skeleton-map preparation step.

## Acceptance gate for every control route

A route is marked `supported` only after all of these pass on the physical RX 6950 XT:

- deterministic dependency discovery;
- graph built from pinned node names and known model assets;
- predictable source/control image resizing;
- control strength visibly affects structure;
- normal generation still works afterwards;
- LoRA coexistence is target-tested or explicitly blocked;
- Gallery/history records enough metadata to understand the run;
- missing dependencies produce an actionable message instead of a broken graph.

## Image editing — first gate complete

Krea 2 whole-image Image Edit is now accepted.

Current product contract:

- source image + natural-language edit instruction;
- whole-image reference conditioning;
- source aspect drives the output after `FluxKontextImageScale`;
- no classic denoise slider;
- regular Krea LoRA remains available;
- Image Edit + Control is intentionally blocked until separately accepted.

### Next edit/reference wave

1. **Material / texture replacement** — focused Image Edit workflow and presets.
2. **One/two-image reference** — explicit content/style reference roles rather than one generic upload field.
3. **Character turnaround sheet generator** — one reference -> front / 3/4 / side / back layout with consistent framing.
4. **Masked Krea editing** — only if a stable provider-native mask route is pinned and target-tested.
5. **Image Edit + Control composition** — separate acceptance gate because memory/model-patch interactions can differ from either feature alone.

## Vector and information graphics

After the image edit/reference wave:

1. **Text-to-SVG**;
2. **Image-to-SVG**;
3. **Infographic-oriented provider/workflow** prioritizing text rendering, layout and diagram reliability.

These should remain separate provider/tool contracts rather than being forced into the raster diffusion interface.

## Later roadmap

### Gaussian Splatting / 3D

Post-v0.3 candidate: local Image(s) -> Gaussian Splat with browser preview and export. FreeSplatter / Vulkan remains the preferred research direction.

### Video

Video is intentionally later than the image-control/edit/reference work. A future implementation needs a separate queue/job UX, asset management and memory acceptance pass before product integration. **MiniMax H3** remains the first candidate to benchmark when the video phase starts; it is not part of the current v0.3 acceptance scope.

## Explicit non-goals for the current pass

- Do not spend the current cycle building SDXL-first ControlNet UX.
- Do not expose fake Canny/Depth/Pose toggles that map to the same underlying graph.
- Do not silently install unpinned or license-unknown custom-node code.
- Do not destabilize accepted Z-Image/Krea txt2img, LoRA, OpenPose or Image Edit paths for speculative throughput gains.
- Do not combine Krea Image Edit + Control until that composition has its own target test.
