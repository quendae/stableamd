# StableAMD v0.3 forward plan

Last updated: 2026-09-14

This document records the agreed execution order after native Z-Image editing was accepted on the target RX 6950 XT 16 GiB machine. `docs/v0.3-status.md` remains the detailed implementation/acceptance log; this file is the execution plan and feature backlog.

## Current accepted baseline

The following paths are already accepted on the target Windows/Radeon system and should not be destabilized while the remaining v0.3 work lands:

- native Windows AMD runtime lifecycle with the pinned TheRock/ROCm + PyTorch + ComfyUI stack;
- SDXL txt2img, img2img, inpaint and outpaint;
- ordered SDXL MultiLoRA;
- Z-Image Turbo txt2img, model-only LoRA, two-LoRA stack, native Inpaint and native Outpaint;
- Z-Image native edit through `Z-Image-Turbo-Fun-Controlnet-Union-2.1-lite-2602-8steps.safetensors`;
- Z-Image Outpaint automatic canvas preparation with 256 px expansion on all four sides;
- Krea 2 Turbo FP8 txt2img;
- classic upscale-after and Gallery upscale for Z-Image and Krea 2;
- curated RealESRGAN/UltraSharp installer path;
- Gallery history/reuse/delete and capability-aware post-generation actions.

A Windows `os error 1455` was observed once while loading the BF16 Z-Image diffusion model after the CPU text encoder was resident. A full reboot cleared the host-memory/commit-pressure state and the same native Outpaint completed. Treat this as a transient Windows commit/pagefile condition rather than a failed edit graph. Compact official Qwen FP4/FP8 encoders remain optional host-memory reductions, not edit prerequisites.

## Immediate v0.3 execution order

### 1. Curated dependency installer

Build a reusable one-click installer pattern for provider dependencies, starting with Z-Image Union 2.1 Lite.

Acceptance:

- product catalog entry with pinned official URL, exact byte size, SHA-256, license and homepage;
- managed destination under `.runtime/stableamd/models/model_patches`;
- temporary download + size/hash verification + atomic promotion;
- existing conflicting file is never silently overwritten;
- Models UI shows `Not installed`, `Installed / restart required`, `Ready`, or integrity failure;
- `Install & activate` restarts only the managed compute backend and refreshes capability state;
- normal StableAMD application process remains running.

This installer pattern should be reusable later for ControlNet/model-patch dependencies instead of adding ad-hoc download commands.

### 2. Krea 2 LoRA

Confirm and then expose real Krea 2 LoRA execution. Do not mark support from filename inference alone.

Implementation/acceptance sequence:

1. inspect the pinned ComfyUI Krea 2 graph and loader compatibility;
2. wire the correct LoRA loader path into the Krea 2 provider;
3. preserve Krea 2 Turbo defaults (`8 steps / CFG 1 / Euler / simple`);
4. test one Krea LoRA on the target RX 6950 XT;
5. if the loader supports composition safely, test two ordered LoRAs;
6. persist the stack in Gallery/history and make Reuse restore it;
7. retest `Upscale after` after LoRA generation;
8. only then change Krea `lora` capability from planned/gated to supported.

### 3. ControlNet / structural guidance

Add ControlNet as a provider-capability layer, beginning with practical stock/validated controls rather than a generic arbitrary-node editor.

First targets:

- Canny;
- Depth;
- OpenPose.

Requirements:

- explicit model/control compatibility by provider/family;
- managed/curated dependency installation where additional models are required;
- reference/preprocessor preview in the UI;
- strength/start/end controls kept compact;
- target-machine acceptance separately for SDXL, Z-Image and Krea 2 where each provider genuinely supports the requested control;
- unsupported provider/control combinations stay hidden or clearly gated.

## High-priority feature block after ControlNet

These are product workflows, not reasons to keep polishing inpaint/outpaint indefinitely.

### Image edit

A first-class Generate mode for general instruction-driven editing from an uploaded/reference image. Prefer provider-native editing; use compatibility-aware fallback only where it is explicit and validated.

### Material replacement

A guided edit workflow for replacing a surface/material while preserving geometry and scene structure, e.g. wood -> marble, fabric -> leather. It may initially be implemented as a specialized image-edit workflow rather than requiring a dedicated model.

### Image/style reference

Support generation from one or two reference images:

- content/reference image;
- optional separate style reference;
- clear distinction between structural/content guidance and style guidance;
- provider-native implementation where possible.

### Character turnaround sheet generator

A preset/workflow that takes one character image and generates a consistent multi-view sheet in one job, targeting front, 3/4, side and back views with a stable character identity and clean sheet layout.

## Later image-tool providers

### Text-to-SVG / image-to-SVG

Treat vector generation as a separate provider/toolchain rather than pretending SVG is another raster diffusion output. Desired tasks:

- text -> SVG icons/illustrations/simple graphic assets;
- image -> cleaned/simplified SVG vectorization;
- downloadable SVG plus Gallery/history provenance.

### Infographic-specialized generation

Evaluate a model/provider that is particularly strong at layout, typography and information-dense graphics. The goal is real infographic/poster/diagram output rather than only decorative image generation.

## Post-v0.3 / later roadmap

### Image(s) -> Gaussian Splat

Already tracked in `docs/roadmap.md` as a v0.4 candidate, preferably through FreeSplatter / `free-splatter.cpp` Vulkan on Windows/Radeon.

### Video

Video is intentionally later because it needs a separate job/queue, preview and export UX plus a much larger memory/runtime envelope. MiniMax H3 is a candidate to benchmark first on the target machine; other video models should be evaluated by actual Windows/Radeon feasibility rather than advertised spec alone.

## Working rule

For every new provider feature: implement the real graph -> keep capability gated -> pass automated regression tests -> target-test on RX 6950 XT -> only then advertise it as supported. Inpaint/outpaint remain available and maintained, but the active v0.3 focus is installer -> Krea 2 LoRA -> ControlNet.
