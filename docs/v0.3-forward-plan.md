# StableAMD v0.3 forward plan

Last updated: 2026-09-21

StableAMD v0.3 now has two implementation-complete but physically unaccepted quality gates: **Character Sheet v2** and **Text-to-SVG v1**. Neither should be called target-accepted until its RX 6950 XT checklist passes.

## Accepted baseline

- Native Windows AMD runtime lifecycle is accepted on RX 6950 XT / 16 GiB.
- SDXL txt2img/img2img/inpaint/outpaint and ordered MultiLoRA remain the compatibility baseline.
- Z-Image Turbo txt2img, ordered model-only LoRA, native inpaint/outpaint, Canny, OpenPose and Depth are accepted/target-tested.
- Krea 2 Turbo FP8 txt2img and model-only LoRA are target-accepted.
- Krea 2 OpenPose, including normal user LoRA + OpenPose, is target-accepted.
- Krea 2 Depth and automatic multi-person DWPose extraction are target-tested.
- Krea 2 whole-image Image Edit is target-accepted.
- RealESRGAN / curated upscale and Gallery reuse remain accepted.
- Long generation requests use serialized async `submit -> poll -> result` transport.

Structural guidance remains provider-first for **Z-Image Turbo and Krea 2 Turbo**; SDXL-first ControlNet expansion stays deferred unless needed for compatibility.

## Character Sheet v2 — physical quality gate remains open

Character Sheet v1 remains only as the explicit `legacy-sequential` comparison path after failing visual acceptance.

The default v2 flow uses Krea 2 Identity Edit v1.2 with the pinned node pack and LoRA, one `1792 x 1024` five-panel base generation, face-only source identity references, guarded local detail passes and non-fatal fallback semantics. BACK never receives face refinement. Heavy Krea passes remain serial and release runtime memory between stages.

The latest architecture specifically avoids reintroducing the head/shoulder identity reference that caused source bleed/ghosting during physical testing. The accepted first detail reference remains face-only; tighter identity correction is limited to appropriate visible-face views.

Character Sheet v2 physical acceptance still requires the same difficult source photographs that exposed v1 weaknesses. Required checks include likeness across visible views, a clean rear view, reduced background/statue leakage, reduced ghost/grid/debris artifacts, repeated-run stability and ordinary Krea Image Edit health afterwards.

Do not tune accepted global Krea txt2img/Image Edit defaults to compensate for a Character Sheet-specific issue.

## Text-to-SVG v1 — implementation complete, physical gate next

Text-to-SVG is now a dedicated **Vector** product workspace, not a mode inside raster Generate.

### Architecture

```text
Vector request
  -> constrained Z-Image raster generation
  -> release GPU runtime
  -> optional border-connected background removal
  -> pinned VTracer
  -> Clean SVG allow-list sanitizer
  -> PNG preview rendered from the final sanitized SVG
  -> persisted Vector history/Gallery record
```

The Vector request surface is intentionally small: Prompt, Style, Detail, Colors, Background, Solid color and Seed. It does not expose sampler/scheduler/LoRA/ControlNet controls.

### Managed tooling

```text
VTracer 1.0.0-alpha.4
resvg_py 0.5.0
```

VTracer installation verifies the pinned release archive size + SHA-256 before atomic promotion. ZIP paths are validated before extraction. `resvg_py` is exact-version pinned. Dependency status is visible in the UI and **Generate SVG** stays disabled until the local toolchain is ready.

### Security and asset contract

The final SVG is allow-list sanitized and complexity-bounded before persistence. Active/unsupported content such as script, embedded image, text, external URL/href, event handlers, DTD/entities and unknown namespaces is rejected.

Raw SVG is not served as a directly navigable browser document. `/api/vector/source` returns JSON only for a persisted sanitized Gallery asset that still matches the canonical sanitizer output. The frontend displays source through `textContent` and creates downloads through a Blob.

Transparent background removal is border-connected rather than a global color delete, preserving enclosed light/white subject details.

### Runtime/job contract

Vector uses the same serialization lock as existing generation jobs, preventing parallel GPU jobs from competing for VRAM. Existing `/api/generate` behavior remains unchanged; Vector submits through its dedicated endpoint and reuses the shared waiter without adding the raster `asyncJob` field.

GPU runtime is released before VTracer/local SVG work.

### Gallery contract

Vector Gallery cards use the PNG preview rendered from the final sanitized SVG, show SVG/vector metadata and suppress raster-only post-actions. Vector actions are:

- Download SVG;
- View source;
- Reuse;
- Delete.

Delete is ownership-aware and refuses arbitrary paths outside StableAMD managed output.

### Automated verification

Development used RED/GREEN coverage for dependency management, sanitization, request semantics, flood-fill background removal, preview generation, shared job serialization, orchestration, safe SVG source/delete lifecycle and dedicated frontend behavior.

Known exact-head milestones:

- Actions #854 — Task 6 lifecycle/source safety: full GREEN;
- Actions #861 — dedicated Vector UI/Gallery behavior: full GREEN.

The final packaging/import/documentation gate must also be GREEN before physical testing starts. The release package must contain all Vector backend/frontend modules, while the final server must still import without eager Pillow/NumPy/`resvg_py` requirements.

Physical worksheet: `docs/v0.3-text-to-svg-test.md`.

Required target samples:

1. simple two-color icon;
2. text-free logo mark/symbol;
3. 4–8 color flat illustration;
4. detailed vector illustration.

For each record raster time, vectorization time, path count, node count, background behavior, SVG result, preview result and Gallery reuse/delete. After all four, run ordinary Z-Image and Krea generation again to verify the Vector workflow did not destabilize the accepted providers.

Do not mark Text-to-SVG `target-accepted` until the worksheet passes on RX 6950 XT.

## Immediate execution order

1. Finish exact-head Text-to-SVG package/import regression and keep PR #4 draft.
2. Pull that exact head onto the RX 6950 XT machine and complete `docs/v0.3-text-to-svg-test.md`.
3. Fix only evidence-backed Text-to-SVG defects found by physical testing.
4. Continue the separate Character Sheet v2 physical quality/stability acceptance until its checklist passes.
5. Begin Image-to-SVG only after the Text-to-SVG contract is physically proven.
6. Then evaluate an infographic-oriented provider/workflow prioritizing text rendering, layout and diagram reliability.

## Image-to-SVG next

Image-to-SVG should reuse the proven local VTracer/sanitizer/preview/lifecycle pieces while defining its own image-input contract. It should not silently broaden Text-to-SVG request semantics or weaken the sanitizer.

Questions for that phase:

- source image upload/managed Gallery reuse contract;
- crop/background controls;
- color reduction behavior;
- vector detail profiles;
- preserving alpha and border-connected removal semantics;
- whether a diffusion cleanup pass is optional or unnecessary.

## Infographic-oriented generation after SVG

This should be treated as a separate provider/tool contract, not another toggle on the diffusion form. Evaluation should prioritize:

- text fidelity and spelling;
- alignment/layout;
- arrows/connectors;
- tables and diagram structure;
- exportability/editability;
- predictable aspect/layout controls.

## Later roadmap

### Gaussian Splatting / 3D

Post-v0.3 candidate: local Image(s) -> Gaussian Splat with browser preview/export. FreeSplatter / Vulkan remains the preferred research direction.

### Video

Video remains later than current image/edit/vector work and needs its own queue UX, asset management and memory acceptance. MiniMax H3 remains a candidate to benchmark later; it is not part of the current v0.3 acceptance scope.

## Explicit non-goals for the current pass

- no SDXL-first ControlNet expansion;
- no fake Canny/Depth/Pose toggles sharing one graph;
- no unpinned/license-unknown custom-node installs;
- no weakening of the Clean SVG allow-list to make traces pass;
- no raw arbitrary SVG browser serving;
- no speculative throughput changes that destabilize accepted Krea/Z-Image paths;
- no Masked Krea editing in this wave;
- no Krea Image Edit + Control composition in this wave.
