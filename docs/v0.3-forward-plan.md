# StableAMD v0.3 forward plan

Last updated: 2026-09-21

This is the active execution order after the accepted Z-Image/Krea generation, LoRA, edit/control, DWPose, Gallery and upscale work. The current release gate is **Character Sheet v2 physical quality/stability acceptance on the RX 6950 XT**.

## Accepted baseline

- Native Windows AMD runtime lifecycle is accepted on RX 6950 XT / 16 GiB.
- SDXL txt2img/img2img/inpaint/outpaint and ordered MultiLoRA remain the compatibility baseline.
- Z-Image Turbo txt2img, ordered model-only LoRA, native inpaint/outpaint, Canny, OpenPose and Depth are accepted/target-tested.
- Krea 2 Turbo FP8 txt2img and model-only LoRA are target-accepted.
- Krea 2 OpenPose is target-accepted, including a normal user LoRA + OpenPose combination.
- Krea 2 Depth is target-tested.
- Automatic multi-person DWPose extraction from a normal photo is target-tested.
- Krea 2 whole-image Image Edit is target-accepted.
- Krea material/texture replacement and one/two explicit content/style/material references are implemented.
- RealESRGAN / curated upscale and Gallery reuse remain accepted.
- Long generation requests use async `submit -> poll -> result` transport.

## Character Sheet v1 — retained only for comparison

The sequential/anchor Character Sheet flow failed visual acceptance. It could complete and compose a sheet, but the known test photograph exposed identity drift, background/statue leakage and repeated artifacts. The later FACE-anchor refinement did not make identity quality reliable enough.

It remains available only through the advanced `legacy-sequential` selector while v0.3 Character Sheet v2 is being accepted. It is not the default and must not be presented as target-accepted.

## Character Sheet v2 — active quality gate

Default Character Sheet now uses **Krea 2 Identity Edit v1.2** with a training-matched graph.

Pinned dependency:

```text
lbouaraba/comfyui-krea2edit

krea2_identity_edit_v1_2.safetensors
SHA-256 6adf9a69cc9502d286db7b69964d37da7e9cfe4b05b4d004bc275f087d3fd3cf
```

StableAMD owns dependency readiness/install state. Missing v2 dependencies produce an actionable install/restart state; the product must never silently run the legacy flow while presenting it as v2.

### Base workflow

One source image produces one five-panel base generation at exactly `1792 x 1024`:

```text
FACE | FRONT | 3/4 | SIDE | BACK
```

Identity Edit acceptance settings are server-owned:

```text
LoRA strength = 1.0
fit_mode      = fit
ref_boost     = 4.0
grounding_px  = 1024
steps         = 10
CFG           = 1
sampler       = euler
scheduler     = simple
denoise       = 1
```

`target_latent` is wired into `Krea2EditModelPatch`. The target stays below the documented 2 MP Identity Edit quality ceiling.

### Panel/detail workflow

After the base generation:

1. release Krea runtime memory;
2. split the base image into five horizontal logical regions;
3. for FACE / FRONT / 3/4 / SIDE, use DWPose to locate a usable face/head region;
4. expand the region for hair/head context and align it to 16 px;
5. run one dual-reference Identity Edit detail job using:
   - image A: the generated panel head crop;
   - image B: the original-source identity crop;
6. release runtime memory after each attempted detail job;
7. blend a successful detail result back with a 12% feather mask;
8. leave BACK unchanged;
9. reassemble the five panels at `1792 x 1024`;
10. persist the final Character Sheet record;
11. only then hide base/detailer intermediate history from the default Gallery.

No Krea jobs run in parallel.

### Failure semantics

Detail children are non-fatal:

- no face -> keep the base panel, `detailerSkipped=no-face`;
- malformed region -> keep the base panel;
- child generation error -> keep the base panel, `detailerSkipped=generation-failed`;
- BACK -> never run DWPose/detail generation, `detailerSkipped=back-view`.

If final persistence fails, intermediate history remains visible for diagnosis.

### Product UI

Default UI now shows **Character Sheet v2 · Identity Edit** and:

## RX 6950 XT Character Sheet v2 acceptance

Use the **same source photographs that exposed the v1 failure** first. Do not substitute an easier source for the first comparison.

Required checklist:

```text
[ ] Identity Edit dependency installs/discovers cleanly
[ ] StableAMD restart activates the node pack + LoRA when required
[ ] one base + serial detailer + final compose completes
[ ] FACE is recognizably the same source person/character
[ ] FRONT is recognizably the same source person/character
[ ] 3/4 is recognizably the same source person/character
[ ] SIDE is recognizably the same source person/character and remains profile
[ ] BACK is a true rear view with no inserted face/portrait
[ ] statue/background leakage is materially reduced versus v1
[ ] ghost/grid/debris artifacts are materially reduced versus v1
[ ] any no-face/detail failure leaves a usable base panel instead of aborting the sheet
[ ] Gallery shows one final Character Sheet card by default
[ ] intermediate base/detail records remain recoverable/traceable
[ ] a second consecutive full v2 run completes
[ ] ordinary Krea Image Edit works immediately after the second v2 run
[ ] no 16 GiB runtime instability appears during the sequence
```

Do not mark Character Sheet v2 `target-accepted` until every item above passes.

## What to record during physical acceptance

For each run capture:

- source image used;
- final Character Sheet screenshot/result;
- dependency status before generation;
- whether each FACE/FRONT/3/4/SIDE detailer completed or skipped and why;
- generation time;
- any ComfyUI/StableAMD error tail;
- whether normal Krea Image Edit succeeds afterwards.

If quality fails, diagnose the exact failing stage before changing parameters. In particular, distinguish:

- wrong base identity conditioning;
- wrong panel geometry/split;
- DWPose face-box failure;
- detail crop too loose/tight;
- Identity Edit child generation issue;
- feather-stitch artifact;
- runtime/VRAM instability.

Do not tune Krea txt2img/Image Edit defaults globally to compensate for a Character Sheet-specific issue.

## Structural guidance — current state

Control remains provider-first for Z-Image Turbo and Krea 2 Turbo. **SDXL is deferred** for ControlNet-first expansion unless needed for compatibility.

Current accepted/implemented surface:

- Z-Image Canny / OpenPose / Depth;
- Krea OpenPose / Depth;
- automatic DWPose extraction;
- curated pose templates and interactive pose editor.

Krea Canny remains gated until a Krea 2-specific route is demonstrated and target-tested.

## Image editing — current contract

Krea whole-image Image Edit remains accepted and unchanged by Character Sheet v2. Material/texture replacement and one/two references remain available. Masked Krea editing and Image Edit + Control composition remain explicitly deferred.

## Execution order after Character Sheet v2 acceptance

1. Text-to-SVG;
2. Image-to-SVG;
3. infographic-oriented provider/workflow prioritizing text rendering, layout and diagram reliability.

These should be separate provider/tool contracts instead of being forced into the raster diffusion interface.

## Later roadmap

### Gaussian Splatting / 3D

Post-v0.3 candidate: local Image(s) -> Gaussian Splat with browser preview/export. FreeSplatter / Vulkan remains the preferred research direction.

### Video

Video remains later than the current image-edit/control/reference work. It requires its own queue/job UX, asset management and memory acceptance pass before product integration.

## Explicit non-goals for the current pass

- no SDXL-first ControlNet expansion;
- no fake Canny/Depth/Pose toggles sharing one graph;
- no unpinned/license-unknown custom-node installs;
- no speculative throughput changes that destabilize accepted Krea/Z-Image paths;
- no Masked Krea editing in this wave;
- no Krea Image Edit + Control composition in this wave.
