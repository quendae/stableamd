# StableAMD v0.3 forward plan

Last updated: 2026-09-15

This is the execution order after the accepted native Z-Image edit path and the target-accepted Krea 2 LoRA path.

## Accepted baseline

- Native Windows AMD runtime lifecycle is accepted on RX 6950 XT / 16 GiB.
- SDXL txt2img/img2img/inpaint/outpaint and ordered MultiLoRA are accepted, but SDXL is no longer the feature-development priority.
- Z-Image Turbo txt2img + ordered model-only LoRA is accepted.
- Z-Image native inpaint/outpaint is accepted with Union 2.1 Lite 2602 8-step.
- Krea 2 Turbo FP8 txt2img is accepted.
- Krea 2 model-only LoRA is target-accepted: `krea2_darkbrush.safetensors` was verified on the RX 6950 XT.
- RealESRGAN / curated upscale and Gallery reuse remain accepted.

## Immediate execution: ControlNet / structural guidance

Control work is provider-first for the models we actually want to use: **Z-Image Turbo and Krea 2 Turbo**. SDXL is deferred unless it is needed as a compatibility fallback.

### Phase C1 — common product contract

Implement one StableAMD control-guidance surface with provider-aware capability gating:

- control image,
- control type,
- strength,
- provider-specific preprocessing/settings only when the actual backend supports them,
- dependency readiness surfaced through `/api/model-support`,
- generation/history metadata that records control type, source and strength,
- no UI option is shown as working before its concrete graph and dependencies are available.

### Phase C2 — Z-Image Turbo

Use the already accepted Alibaba PAI **Z-Image Fun ControlNet Union 2.1 Lite** patch rather than adding a second large control model.

Order:

1. **Canny** — first target. The pinned ComfyUI already provides the core `Canny` node, so a normal source image can be preprocessed inside the graph and fed to `ZImageFunControlnet.image`.
2. **Depth** — next, after selecting a lightweight/local depth preprocessor that behaves reliably on the managed AMD runtime.
3. **Pose / OpenPose** — after the pose preprocessor path is pinned and target-tested.

First Canny gate:

- regular source image upload,
- low/high Canny thresholds,
- control strength,
- 8-step Z-Image Turbo defaults,
- existing Union 2.1 Lite patch,
- normal txt2img must still work immediately afterwards.

### Phase C3 — Krea 2 Turbo

Krea 2 does not have one stock ComfyUI ControlNet path equivalent to SDXL, so routes are accepted independently.

Order for Turbo:

1. **OpenPose map** — first product path. Use the MIT `ComfyUI-Krea2-Ostris-Edit` integration plus the Apache-2.0 `krea2_turbo_openpose_controlnet.safetensors` adapter. First gate accepts an already prepared OpenPose/DWPose skeleton map; automatic DWPose preprocessing follows separately.
2. **Depth** — use `Patil/Krea-2-depth-controlnet` (works with Turbo according to its model card) once a suitable, redistributable/managed ComfyUI integration and depth preprocessor are pinned.
3. **Canny** — keep gated until a Krea 2 **Turbo** route is validated. Current public Canny/NK2E routes are not treated as equivalent to a proven Turbo ControlNet implementation.

The first Krea OpenPose dependency installer may install only pinned, license-known components. Community integrations without a declared license are not vendored into StableAMD.

## Acceptance gate for every control route

A route is marked `supported` only after all of these pass on the target RX 6950 XT:

- dependency discovery is deterministic,
- the graph is built from pinned node names and known model assets,
- the source/control image is accepted and resized predictably,
- control strength visibly affects structure,
- normal generation still works after the controlled generation,
- LoRA coexistence is either target-tested or explicitly blocked for the first gate,
- Gallery/history records enough metadata to reproduce the run,
- missing dependencies produce an actionable message instead of a broken graph.

## After ControlNet

Next feature wave, in this order unless target testing reveals a blocker:

1. **Image edit** — first-class edit entry, not only a Gallery post-action.
2. **Material replacement** — material/texture replacement as a focused edit workflow.
3. **Image/style reference** — one or two reference images with explicit content/style roles.
4. **Character turnaround sheet generator** — one reference -> front / 3/4 / side / back sheet with consistent layout.
5. **Text-to-SVG and image-to-SVG** — separate vector-oriented provider/toolchain.
6. **Infographic-oriented model/workflow** — prioritize text rendering, layout and diagram reliability.

## Later roadmap

### Gaussian Splatting / 3D

Post-v0.3 candidate: local Image(s) -> Gaussian Splat with browser preview and export. FreeSplatter / Vulkan remains the preferred research direction.

### Video

Video is intentionally later than the image-control/edit/reference work. MiniMax H3 is a candidate because it may be realistic on the target hardware, but it requires a separate queue/job UX, asset management and memory acceptance pass before product integration.

## Explicit non-goals for the current ControlNet pass

- Do not spend the current cycle building SDXL-first ControlNet UX.
- Do not expose fake Canny/Depth/Pose toggles that map to the same underlying graph.
- Do not silently install unpinned or license-unknown custom-node code.
- Do not destabilize the accepted Z-Image/Krea txt2img or LoRA paths to gain ControlNet support.
