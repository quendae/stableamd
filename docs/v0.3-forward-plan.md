# StableAMD v0.3 forward plan

Last updated: 2026-09-20

This is the active execution order after the accepted native Z-Image edit/control paths, target-accepted Krea 2 LoRA/OpenPose/Depth paths, target-accepted Krea 2 whole-image Image Edit, working one/two-image references, material replacement, and target-tested automatic DWPose extraction from normal photographs.

## Accepted baseline

- Native Windows AMD runtime lifecycle is accepted on RX 6950 XT / 16 GiB.
- SDXL txt2img/img2img/inpaint/outpaint and ordered MultiLoRA remain the compatibility baseline.
- Z-Image Turbo txt2img + ordered model-only LoRA is accepted.
- Z-Image native inpaint/outpaint is accepted with Union 2.1 Lite 2602 8-step.
- Z-Image Canny, OpenPose map and Depth control routes are target-tested.
- Krea 2 Turbo FP8 txt2img is accepted.
- Krea 2 model-only LoRA is target-accepted.
- Krea 2 OpenPose is target-accepted, including coexistence with a normal user LoRA.
- Krea 2 Depth is target-tested.
- Automatic multi-person DWPose extraction from a normal photo is implemented and target-tested with body + hands + face.
- Krea 2 whole-image Image Edit is target-accepted.
- Krea material/texture replacement and explicit content/style/material reference roles are implemented on top of Image Edit.
- RealESRGAN / curated upscale and Gallery reuse remain accepted.
- Long generation requests use the async `submit -> poll -> result` transport.

## Character Sheet — active quality gate

The old single-pass four-view turnaround experiment has been replaced in the product UI by **Character Sheet**.

Implemented flow:

1. one source character image;
2. five independent sequential Krea Image Edit generations:
   - Face close-up;
   - Front;
   - 3/4;
   - Side;
   - Back;
3. one persisted, non-generative composite PNG assembled from those five results;
4. one final Character Sheet Gallery entry, while the five child views remain linked intermediate assets.

### Framing modes

The UI exposes:

- **Auto** — default;
- **Portrait** — head / shoulders / torso;
- **Full body** — head to toe.

Auto reuses the managed DWPose runtime for human sources. It classifies a detected subject as portrait or full-body from visible keypoints and creates a subject-focused reference crop without stretching the source. Face close-up gets a tighter face/head reference crop.

If DWPose does not recognize the source — for example a stylized/non-human character — StableAMD does **not** apply an aggressive human crop. It preserves the source framing/aspect and asks Krea to retain approximately the same visible-body coverage.

### Per-view output contract

- Face close-up: `1024 x 1024`;
- Portrait Front / 3/4 / Side / Back: `896 x 1152`;
- Full-body Front / 3/4 / Side / Back: `832 x 1216`;
- unrecognized Auto fallback: approximately 1 MP while preserving source aspect, aligned to 16 px.

The prompt is framing-aware: portrait jobs no longer receive a contradictory `head to toe` instruction, full-body jobs still do, and unknown-source fallback avoids inventing a forced full body merely because the task is a sheet.

### Composite / Gallery contract

After all five generation jobs succeed, StableAMD creates the final image locally without another diffusion pass:

- layout: `grid-3x2`;
- row 1: Face / Front / 3/4;
- row 2: Side / Back, centered;
- labels: `FACE / FRONT / 3/4 / SIDE / BACK`;
- each child is fit with preserved aspect ratio;
- composite is stored as a normal StableAMD output/history record;
- child records are marked `galleryHidden=true` only after the composite succeeds and receive their parent PromptId/ImagePath.

This prevents the main Gallery from becoming five near-duplicate cards while retaining every generated source view for traceability.

### Automated gate

Character Sheet code + regression changes passed **GitHub Actions #737** end-to-end: PowerShell parse, Python API/regression tests, Pester/unit tests, package build and artifact upload. The remaining gate is physical quality acceptance on the RX 6950 XT.

### RX 6950 XT acceptance checklist

Character Sheet is **implemented but not yet target-accepted**. Before promotion to accepted status, verify on the physical RX 6950 XT:

- Auto correctly detects the supplied landscape portrait source and crops around the subject rather than spending reference area on empty background;
- Face close-up stays recognizably the same person/character;
- Portrait Front / 3/4 / Side / Back keep acceptable identity, clothing and color consistency;
- Side is a real side profile and Back is a real rear view rather than another front-facing portrait;
- Full body override produces usable complete-body views;
- a non-human/unrecognized source falls back to source framing without destructive human cropping;
- final `grid-3x2` composite is persisted and shown as one Gallery card;
- child assets remain linked/recoverable but hidden from the default Gallery;
- a normal Krea Image Edit generation still works after a complete Character Sheet run;
- repeated Character Sheet runs do not destabilize the 16 GiB runtime.

## Structural guidance — current state

Control work remains provider-first for **Z-Image Turbo and Krea 2 Turbo**. **SDXL is deferred** unless required as a compatibility fallback.

Current accepted/implemented surface:

- Z-Image Canny through the accepted Union 2.1 route;
- Z-Image OpenPose map through Union 2.1;
- Z-Image Depth using the shared managed Depth Anything V2 Small preprocessor;
- Krea OpenPose using the pinned Krea/Ostris path;
- Krea Depth using the pinned Krea 2 Control LoRA route plus the shared depth preprocessor;
- automatic DWPose extraction from normal photographs, including multi-person body + hands + face output;
- curated pose templates and the interactive pose editor.

Krea **Canny** stays gated until a Krea 2 Turbo-specific route is demonstrated; unrelated public Canny examples are not treated as equivalent without target proof.

## Acceptance gate for every control route

A route is marked `supported` only after all of these pass on the physical RX 6950 XT:

- deterministic dependency discovery;
- graph built from pinned node names and known model assets;
- predictable source/control image resizing;
- control strength visibly affects structure;
- normal generation still works afterwards;
- LoRA coexistence is target-tested or explicitly blocked;
- Gallery/history records enough metadata to understand the run;
- missing dependencies produce an actionable message instead of a broken graph.

## Image editing — current product contract

Krea 2 whole-image Image Edit is accepted.

Current behavior:

- source image + natural-language edit instruction;
- whole-image reference conditioning;
- normal Image Edit follows source aspect after `FluxKontextImageScale`;
- no classic denoise slider;
- regular Krea LoRA remains available;
- focused material/texture replacement is implemented;
- one/two-image references support explicit content/style/material roles;
- Character Sheet is the active quality/acceptance gate described above;
- Image Edit + Control stays blocked until a later dedicated acceptance pass.

### Explicitly deferred for now

- **Masked Krea editing** — postponed; do not spend the current pass on mask UX/provider-native masking.
- **Image Edit + Control composition** — postponed; keep Image Edit and Control as separate accepted paths for now.

## Execution order after Character Sheet acceptance

1. Text-to-SVG;
2. Image-to-SVG;
3. infographic-oriented provider/workflow prioritizing text rendering, layout and diagram reliability.

These should remain separate provider/tool contracts rather than being forced into the raster diffusion interface.

## Later roadmap

### Gaussian Splatting / 3D

Post-v0.3 candidate: local Image(s) -> Gaussian Splat with browser preview and export. FreeSplatter / Vulkan remains the preferred research direction.

### Video

Video is intentionally later than the image-control/edit/reference work. A future implementation needs a separate queue/job UX, asset management and memory acceptance pass before product integration. **MiniMax H3** remains the first candidate to benchmark when the video phase starts; it is not part of the current v0.3 acceptance scope.

## Explicit non-goals for the current pass

- Do not spend the current cycle building SDXL-first ControlNet UX.
- Do not expose fake Canny/Depth/Pose toggles that map to the same underlying graph.
- Do not silently install unpinned or license-unknown custom-node code.
- Do not destabilize accepted Z-Image/Krea txt2img, LoRA, OpenPose or Image Edit paths for speculative throughput gains.
- Do not implement Masked Krea editing in the current wave.
- Do not combine Krea Image Edit + Control in the current wave.
